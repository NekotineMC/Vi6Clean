- (event) 2026-10-28 fresh start of the bot project; this memlog restates the current decisions only, replacing the earlier history
- (direction by user) Two pains, one bot: fill lobbies that lack players, and run whole games unattended as regression tests, since there is no test harness
- (direction by user) Vi6 is played 2v2 on average and never beyond 3v3, on a small, self-hosted, offline-mode, friends-only server; cheating is not a concern
- (direction by user) Bots are the operator's own tool: ugly and command-only is fine; no skins, crafted names or passing as human
- (capability) CAP-1 Runtime bot control. intent: the operator adds and removes bots on a running server, choosing count and team, without a restart. success: one command adds N bots, a list command reports them, another removes them, no restart in between
- (capability) CAP-2 Player parity in the game layer, including dialogs. intent: a bot is treated exactly as a human by team assignment, phases, scoring, cleanup and dialogs. success: a bot game runs the full phase sequence to a recorded result with no bot branch in Vi6 game logic, and with no human connected bots answer the lobby dialog through the unmodified production lambda and the lobby advances
- (capability) CAP-3 Tool use. intent: a bot holding a tool triggers the handlers a human triggers. success: every handler gated on interact, move, held-slot, sneak and sprint is reachable and the tool's effect occurs
- (capability) CAP-4 Visible autonomous activity. intent: a bot moves and navigates on its own. success: with no operator input a bot travels between map areas for the whole round, respecting the map entrance and exit rules
- (capability) CAP-5 Unattended game execution. intent: a complete game runs with zero humans. success: 4-bot and 6-bot runs each reach a win condition with the result in the log and no exception, started by one console command, repeatable from a clean roster
- (decision) CAP-6 is retired (dialog responses were folded into CAP-2); the ID is never reused
- (capability) CAP-7 Reusable bots. intent: any Nekotine minigame spawns, drives and removes bots through one library API without NMS code of its own. success: a second plugin depending on NekotineBots spawns a bot, makes it use an item and removes it, and Vi6 uses the same API
- (capability) CAP-8 Close-range combat. intent: a bot fights at melee range in Vi6 PvP. success: in a 1v1 against a human the bot targets, aims, keeps distance, strafes and lands hits respecting cooldown and reach without server snap-backs
- (decision) Bots are our own fake ServerPlayers joined through PlayerList.placeNewPlayer on a fake Connection backed by an EmbeddedChannel: in getOnlinePlayers, isOnline true, join and quit events fire, admission may use Vi6's normal join path
- (decision) Own implementation written from scratch; egors-fakeplayer and the other reference plugins are inspiration only; their direct gameMode, setSelectedSlot, setShiftKeyDown calls and Carpet features are not reproduced; verbatim snippets keep their MIT notice
- (constraint) Every input reaches Vi6 through a real ServerGamePacketListenerImpl handler with a real serverbound packet: no fabricated event, no direct game-mode call, no bot branch in game logic
- (constraint) Bot packets are written inbound into the fake connection's channel so ProtocolLib inbound listeners see them like human packets
- (constraint) The body acknowledges teleports (one ack per id, latest only, next tick, never inside send) and sends player-loaded after join and each respawn; it ticks itself because nothing ticks a fake connection
- (constraint) Movement computes the next position with the server's own physics and submits it through handleMovePlayer so PlayerMoveEvent fires; PlayerFailMoveEvent diagnoses refusals
- (decision) NekotineBots is a library, not a plugin: own repository, included in Vi6Clean as a git submodule and Gradle subproject like NekotineCore, shaded into each host; Bukkit-only public API; hosts own behaviour and call its lifecycle hooks; each host has its own roster
- (decision) NekotineBots stays out of NekotineCore so Core is not pinned to a Paper build; no required dependency on Core, but it may take one when needed
- (constraint) Small NMS surface (about 25 types in 2-3 files), minimal reflection, startup self-test that fails loudly at boot
- (decision) One Minecraft version per release, moving with Vi6: 26.3, then 26.4 as Paper and ProtocolLib allow
- (decision) Written in Java, not Kotlin; no compile-time null-check tooling required
- (constraint) Sized for 2v2 to 3v3: lobby fill 1-5 bots, unattended runs 4 bots typically and 6 at most
- (decision) Bots are ephemeral pawns: removed when the host plugin disables, never persisted or restored across restart or /reload
- (constraint) Bot failures are loud: behaviour exceptions are caught and logged with the bot name and phase
- (constraint) Bot names at most 16 characters; stable offline-mode names and UUIDs, or cleanup deletes playerdata and usercache entries
- (constraint) Dev server needs spawn-protection=0 (it has 16), or non-op bots cannot click blocks near spawn
- (decision) Long-range travel via A* over Bukkit block data, the Pathetic library or a per-map navigation graph; close-range PvP is a per-tick reactive controller; Baritone does not run server-side
- (constraint) Verification is a booted dev server over RCON and its log; no JVM test suite
- (decision) Rejected: MCProtocolLib loopback clients (hand-written client physics), Mineflayer (upstream stuck at 26.1), a HeadlessMC plus Baritone test layer (packet bots cover server-side logic)
